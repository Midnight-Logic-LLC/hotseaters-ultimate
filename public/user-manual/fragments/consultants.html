Consultants

The Consultants page manages team members, their roles, consultant tiers, service qualifications, invitation state, and Google Calendar connections. It is the primary surface for inviting new users into a tenant and keeping who-does-what accurate.

All data is persisted in the Supabase user_profiles, user_roles, consultant_tiers, and service_qualifications tables, scoped by tenant_id. Invitations are sent through Supabase Auth plus a Resend email that points to /accept-invite. Related: Settings, Database Schema, Notification System.

Header controls

Title "Team" with a "Manage your team members" subtitle.

  • Invite Team Member — Visible to owner and admin when tenant_firms.subscription_tier = 'multi_user'. Opens the inline invite form.
  • Single-user upgrade notice — If subscription_tier = 'single_user', owner and admin see an amber card prompting upgrade to the Multi-User plan with pricing info and a link to the Pricing page.

Invite form

Inline card form:

  • First Name / Last Name — Optional; pre-fills the invitation record.
  • Email Address — Required; the invitation email is sent here.
  • Role — Admin, Sales, or Trial Consultant.
  • Team Member Tier — Populated from active consultant_tiers rows (shows name and multiplier).

Submitting calls the invite-team-member Edge Function which:

  1. Creates a pending invitation row (tenant_id, email, name, role, consultant_tier_id, token, invited_by).
  2. Issues a Supabase Auth invite for that email.
  3. Sends a Resend email with the invitation link pointing at /accept-invite.

Cancel clears and closes the form.

Coexistence with OAuth sub-user approval

If a new user signs in via OAuth before their invitation is accepted, the invitation email acts as the linking token — the OAuth account is matched to the pending row on accept, the role and tier are applied, and the user lands in the tenant. Owner and admin still see the pending entry in the Pending Invitations panel until it is accepted or cancelled.

Filter bar

  • Search — Filters by first name, last name, or email (case-insensitive).
  • List / Card toggle — Animated pill toggle. Persisted to user_profiles.preferences.teamViewType. Default: card.
  • Active / Inactive switch — Owner and admin only. When toggled to Inactive, shows only consultants where is_active = false.

Consultant groups

Consultants are grouped into collapsible sections:

  • By Consultant Tier — Each tier gets its own section with a colored bar, tier name, multiplier (e.g. ×1.0), and member count. The header is clickable to collapse. Members are sorted alphabetically by last name, then first name.
  • HotSeatHub Favorites — Favorited subcontractor consultants from other tenants, resolved from the favorites network. Rendered read-only with the HSH primary color.
  • No Tier — Consultants without a consultant_tier_id. Uses a neutral-colored bar.

Consultant card / row

Each consultant renders as a card (grid) or a list row depending on teamViewType. Both show:

  • Profile photo, or a gradient initials avatar with first + last initials.
  • Full name, title (italic), email, phone (formatted).
  • Assigned services list — resolved from service_qualifications, sorted by category and service order.
  • Tier badge, color-coded by multiplier — purple for ≥ 1.2, blue for ≥ 1.0, green otherwise.
  • Role badge — Owner, Admin, Sales, or Trial Consultant.
  • Google Calendar status badge — Connected, Expired, Checking, or No Calendar. Health is checked per consultant via an Edge Function on mount.
  • Inactive badge — shown when is_active = false; the card renders at 60% opacity.

Click behavior: owner and admin open the form in edit mode; own profile opens in edit mode; other users see the form in read-only mode.

Consultant form

Inline edit form that replaces the list or grid. Fields depend on permissions:

  • All users editing own profile — First name, last name, phone, title, profile photo upload, signature image upload.
  • Owner / admin editing any member — All of the above, plus role dropdown (Admin / Sales / Trial Consultant — cannot change own role), tier dropdown, service qualification checkboxes (grouped by service category, sorted by category and service order), active / inactive status, and Google Calendar connect / disconnect.
  • Read-only mode — All fields displayed as text with no edit controls; shown when a non-admin views another member.
  • Deactivate — Available in the form for owner and admin.
  • Reactivate — Available for inactive members.

On save, updates user_profiles and replaces the consultant's service_qualifications rows (deletes existing, bulk-inserts the newly selected service_id values). Non-admins editing their own profile can only update personal fields — role, tier, status, and qualifications are preserved from the original data.

Pending invitations

A yellow card above the team list showing all pending invitations for the current tenant. Each row shows name (or email when no name is set), email, role badge, and a red Cancel button that deletes the invitation and revokes the Supabase Auth invite.

Deactivation flow

An alert dialog titled "Deactivate Team Member" explains that historical data (time entries, expenses) is preserved. Confirming sets user_profiles.is_active = false. The member disappears from the active list but appears when toggling to Inactive, where a Reactivate button is available.

URL parameters

?editConsultantId=ID — Checked on mount and when the consultant list loads. If present, auto-opens that consultant's edit form and cleans the URL. The page listens for popstate events (for sidebar profile clicks) and for postMessage events of type calendar_connected (from the Google Calendar OAuth popup) to refresh the consultant and show a success toast.

Entity mappings

  • UserInfo → user_profiles + user_roles
  • UserService → service_qualifications
  • Tier → consultant_tiers
  • company_id → tenant_id (enforced by RLS on every query)
